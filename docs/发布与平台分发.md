# 发布与平台分发

> 维护者手册：一份源码怎么同时出 macOS 与 Windows 安装包、怎么发版、怎么验收、出事怎么回滚。
> 面向要动发布流程的人；普通用户看 [`使用手册.md`](使用手册.md)，改代码看 [`开发指南.md`](开发指南.md)。

---

## 0. 原则

**一份源码 + 三层分流，不拆仓库、不做长期分叉分支。**

| 层 | 负责什么 | 落地位置 |
| --- | --- | --- |
| 运行时 | 界面文案、快捷键符号、权限模型、图标、声音后端 | `sys.platform` 判断 + `app/platform/platform_text.py` |
| 构建时 | 各自的依赖、构建脚本、图标文件 | `requirements-macos.txt` / `requirements-windows.txt`；`build_macos.sh` / `build_windows.ps1`；`icon.icns` / `icon-windows.ico` |
| 分发时 | 安装包按平台命名，脚本各自只挑自己那份 | Release 资产 `*-macos.dmg` / `*-windows-setup.exe`；`install_sayo.sh` / `install_sayo.ps1` |

拆成两个仓库或两条长期分叉的源码分支，每个功能都要改两遍，版本必然漂移。

## 1. 动手前先确认仓库状态

- 远程 `main` 是唯一主干：**macOS 与 Windows 共用同一份源码**，Windows 支持已并入 `main`（v1.0.1 起）。
- 历史版本页：`v1.0.0` 与 `v1.0.1` 都是**双平台同一页**（DMG / PKG / Windows setup.exe 各有自己的 `.sha256`）；`v1.0.0` 的 Windows 包是后补的，`v1.0.1` 从一开始就是双平台发布。两个版本页都保留一个 `install_models.command`（断网机器离线部署用，不要删）。
- 发布前先看 `commits/main` 最新 sha 与自己本地/分支基线是否一致；**上游随时可能又推提交**（见 3.4）。
- 本地工作副本可能是**快照**而非 `git clone` 得到的（没有共同祖先）。动手前先检查：

```bash
git fetch origin
git log --oneline -1
git merge-base HEAD origin/main || echo "无共同祖先：本地方是快照，绝不能直接 push/强推 main"
```

- 没有共同祖先时，**只能用「以远程 main 为父提交开新分支」的方式提交**（第 3.2 节的 API 路径就是干这个的），
  绝不能 `git push -f origin main`。

---

## 2. 版本号只有一个来源

- 唯一来源：`app/config.py` 的 `APP_VERSION`。
- 安装包名、安装器版本、macOS `CFBundleShortVersionString`、Windows 应用列表里的版本，全部从它派生：
  - `scripts/build_windows.ps1` 读出后传给 ISCC（`/DMyAppVersion=...`），`packaging/windows.iss` 里只留兜底默认值。
  - `packaging/sayo.spec` 读出后写入 `CFBundleShortVersionString` / `CFBundleVersion`。
  - `build_macos.sh` / `build_linux.sh` 读出后用于产物命名。
- **发版只改这一处**；改完检查产物名是否跟着变（`sayo-<版本>-windows-setup.exe`、`sayo-<版本>-macos.dmg`）。

## 3. 发版流程

### 3.1 正常路径（能访问 github.com）

```bash
git checkout -b feat/<主题> origin/main
# ...改动、本地测试...
git push -u origin feat/<主题>
# 网页开 PR → CI 跑 macOS + Windows 两个作业 → 合并进 main
git tag v<版本> && git push origin v<版本>
```

推 `v*` 标签会触发 `.github/workflows/release.yml`：macOS 与 Windows 各构建各的，
产物（含各自 `.sha256`）合并挂到**同一个 Release**。两平台资产必须在同一页，
这样 `install_sayo.*` 无论从哪台机器跑都能取到本平台那一份。

### 3.2 备选路径（git 协议不可用，只有 REST API 通）

`scripts/publish_api.py` 用 API 造提交，父提交是远程 `main`，效果等价于「以 main 为父开分支并 push」，
不需要 `github.com` 可达，也不需要本地有远程历史对象。

```bash
python scripts/publish_api.py                       # 只预览：列出改动/新增/删除、安装包与 sha256
GITHUB_TOKEN=<PAT> python scripts/publish_api.py    # 真提交：建分支 + 挂安装包与 .sha256
```

它做的事：

1. 读远程 `main` 的 tree，得到基线（路径 + blob sha + mode）；
2. 把差异文件作为 blob 上传，**沿用远程 mode**（新脚本按扩展名给 `100755`），不会把可执行位改掉；
3. 合成新 tree + 新 commit（父提交 = 远程 main）；
4. 建/更新分支 `feat/<主题>`（`force: false`，不覆盖别人的提交）；
5. 把 `dist/` 里的 Windows 安装包**连同同名 `.sha256`** 上传到指定 Release；
6. `--yes-merge` 才会去合并，默认不合并。

常用参数：

| 参数 | 用途 |
| --- | --- |
| （无） | 预览：只打印改动/新增/删除、安装包与 sha256，不写任何东西 |
| `--force-ref` | 基线已前进、分支不再是 main 的后代时，允许把分支重建到新基线上（PR 保留，只换提交历史） |
| `--allow-delete` | 允许删除远程文件；**默认拒绝**，见下面这条护栏 |
| `--asset <路径>` | 指定要上传的安装包；`--asset /none` 表示本次只推源码 |
| `--release-tag v1.0.1` | 挂到哪个 Release 页（与 mac 资产并列） |

安全设计（别改坏）：

- 删除判定只认「远程有、本地没有、**且没被 `.gitignore` 忽略**」的路径。
  本地 walk 会跳过被忽略的文件，若直接按「本地没有 = 删除」处理，远程一旦存在命中忽略规则的文件，
  一次推送就会把它从仓库里删掉。
- 安装包上传前先算 sha256 并一起传；缺 `.sha256` 时安装脚本的校验分支会被跳过，等于没有校验。
- **删除护栏**：脚本以本地工作副本为唯一真相。上游刚推了新文件、你还没同步时，那个文件在本地不存在，
  会被判成「你删了它」——一次推送就把别人的提交抹掉（v1.0.1 合并期间真实发生过：覆盖掉了
  `assets/icon-rounded.png` 与 `make_icon.py` 的改动）。所以带删除的推送默认直接中止，
  确认要删才加 `--allow-delete`。
- 所有读接口也带 token：未认证只有 60 次/小时配额，批量推几次就 `403 rate limit exceeded`。

> **不要用 `--create-release` 单独开一个只有 Windows 资产的正式版**：macOS 用户的安装脚本按「最新正式版」查找，
> 会取到那一页却找不到 dmg。要发新版本就合并进 `main` 后打标签，让 `release.yml` 一次出两个平台；
> 只想临时挂包，就挂到**已有版本页**（与 mac 资产并列）。

### 3.3 上游同时在改 `main` 怎么办

多人在不同机器上同时往 `main` 推是很正常的状态（另一台机器在改 macOS 侧文档时尤其频繁）。
API 路径下每次推送前都要走一遍：

```bash
# 1. 看 main 有没有动
curl -s -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/<owner>/<repo>/commits/main | grep -m1 '"sha"'

# 2. 预览：确认「删除」列表为空（非空说明自己的副本落后了）
python scripts/publish_api.py --base main
```

- `删除` 非空 → 先把自己缺的上游文件拉进工作副本，再推；**不要**用 `--allow-delete` 硬推。
- 要让分支跟上新基线：`--base main --force-ref`（新提交的父 = 最新 main）。
- 冲突文件用三方合并解决，base 取「分支原基线」而不是最新 main：

```bash
git merge-file -p <我的版本> <基线版本> <上游最新版本> > merged   # 返回 0 表示无冲突
```

- 合并 PR 时若报 `405 Pull Request has merge conflicts` 或 `mergeable_state: unknown`，
  通常是 `main` 在你推送后又前进了：重新走一遍本节，再合并。

### 3.4 命名约定（脚本依赖，改名前先看这里）

| 类型 | 命名 |
| --- | --- |
| macOS 安装包 | `sayo-<版本>-macos.dmg` / `.pkg` |
| Windows 安装包 | `sayo-<版本>-windows-setup.exe` |
| Windows 免安装 | `sayo-<版本>-windows-x64.zip` |
| 校验文件 | 上述文件 + `.sha256`（内容格式 `hash  filename`） |

## 4. 验收（不要只看脚本自述）

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| 1 | `main` 未被改写 | 推分支前后 `commits/main` 的 sha 一致；已有标签（`v1.0.0` / `v1.0.1`）都还在 |
| 2 | 分支内容正确 | 分支 tree 含 `app/platform/platform_text.py`、`assets/icon-windows.ico`、`.github/workflows/release.yml` |
| 3 | 没把二进制带进 git | 分支 tree 里搜不到 `dist/`、`.exe`、`models/*.onnx` |
| 4 | macOS 资源未被改 | `assets/icon.png` / `icon.ico` 的 blob sha 与改动前一致 |
| 5 | 测试通过 | 两侧 `pytest -q tests` 均通过（Windows 全量 160 passed / 14 skipped；4 条 macOS 专用用例在 Windows 上跳过） |
| 6 | 安装包可装可卸 | 装完桌面 1 个图标、应用列表显示「轻述 sayo」；卸载后程序目录与注册表项清空，`%APPDATA%\sayo` 数据保留 |
| 7 | 包与源码对应 | 安装包版本 = 标签版本 = `app/config.py` 的 `APP_VERSION` |
| 8 | 资产可校验 | 每个安装包都有同名 `.sha256`，`shasum -a 256 -c` / `Get-FileHash` 通过 |
| 9 | 上游改动没被吃掉 | 合并后 `main` 的 tree 里仍能找到合并期间上游新增的文件（例如 `assets/icon-rounded.png`） |

macOS 侧另需在真机跑一次 `bash scripts/build_macos.sh`，启动后确认界面仍是 `⌘` / `菜单栏` / `辅助功能`、
图标无白边——这一步不能用推理代替。

## 5. 红线

1. **不要 `git push -f origin main`**：本地若是快照，一推就抹掉 macOS 的全部历史。
2. **不要把 `dist/`、`.exe`、`models/*.onnx` 提交进 git**：单文件 100 MB 硬上限，二进制进历史后无法真正删除。
3. **不要为了「只拉自己平台的代码」拆仓库或长期分叉两条源码分支**。
4. **PowerShell 脚本必须 UTF-8 with BOM**（Windows PowerShell 5.1 否则中文乱码），且只有一个 BOM。
5. **中文提交信息走 `git commit -F <utf-8 文件>`**（PS 5.1 按 GBK 传参会乱码）。
6. 资产名必须保持第 3.4 节的模式，否则 `install_sayo.*` 认不出来。

## 6. 回滚

| 想撤销 | 做法 |
| --- | --- |
| 分支 | `git push origin --delete <分支>`，或网页删除分支 |
| Release 资产 | GitHub → Releases → 该资产右侧 Delete |
| 已合进 main 的提交 | `git revert -m 1 <merge-sha>` 后推新提交（不要 reset 后强推） |
| 本地未提交改动 | `git stash push -u` 先存，再 `git checkout -- .` |

## 7. 常见失败对照

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `401 Bad credentials` | token 错或过期 | 重新生成，勾 `repo` |
| `403 Resource not accessible by personal access token` | 权限不足 | 勾 `repo`；要改 `.github/workflows/` 再勾 `workflow` |
| 读 tree 阶段 `404` | 仓库路径或分支名不对 | 核对仓库名与基线分支 |
| 附件上传 `502` / 卡住 | 上传通道波动 | 重跑同一条；已有同名资产会跳过，要替换先在网页删除 |
| 安装脚本提示「没有匹配文件」 | 资产命名不符约定，或包只挂在预发布页 | 按第 3.4 节改名；把包挂到正式版页面 |
| 装完图标仍是旧的 | 图标缓存 | 安装器已自动刷新；仍异常时执行 `ie4uinit.exe -ClearIconCache` 后重启资源管理器 |
| 合并 PR 报 `405 Pull Request has merge conflicts` | `main` 在你推送后又前进了 | 重新以最新 main 为基线 `--force-ref` 推送，再合并（3.3） |
| 更新分支报 `422 Update is not a fast forward` | 基线动了，旧分支不再是后代 | 加 `--force-ref` 重建分支 |
| 读接口 `403 rate limit exceeded` | 未带 token，用的是未认证配额 | 传 `GITHUB_TOKEN`，脚本的读接口会一起带上 |
| 推完发现上游新文件没了 | 本地没同步，被当成「删除」 | 加删除护栏后默认会中止；已发生的用第 2 步把文件补回来再推 |

## 8. 分发之后

- 安装包**不含语音模型**：macOS 由用户跑一次下载脚本；Windows 首启由应用在后台下载（校验 SHA-256、失败重试）。
  这一点要写进 Release 说明，否则用户会以为「装完不能离线」。
- Windows 安装包**未做代码签名**：首次运行会弹 SmartScreen「未知发布者」，属预期行为。
  要消除它需要 OV/EV 证书并在构建机用 `signtool` 签名，签名后再发版。
- 校验和随包发布，README 与 Release 说明都要给出校验方法。
